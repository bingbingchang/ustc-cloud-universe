# 模块分工与迭代计划

这里是团队接手的建议拆分，没有据此新建背包、账号、房间或数据库。负责人待团队认领；一个人可以负责多个模块，不要求凑齐相同数量的人。

## 1. 当前基础和缺口

| 模块 | 已有基础 | 还需要做的内容 |
|---|---|---|
| 世界与建筑 | 东区外部场景、道路、碰撞、独立精细样景 | 建筑细化、室内、出入口、逐区美术与性能 |
| 玩家 | 走跑跳、镜头、学生外观 | 持久角色身份、外观选择、角色信息面板 |
| UI | 功能性HUD、坐标、区域菜单、NPC列表与对话、联机文字输入 | 统一视觉、布局与多分辨率、角色与系统窗口 |
| NPC与AI | 15位人物、六类动作、按角色过滤的RAG | 内容与体验打磨、更多互动及多人环境中的行为约定 |
| 联机 | ENet会话、移动复制、聊天、无窗口主机 | 账号与角色ID、共享世界规则、权威物品与房间状态、目标人数验证 |
| 背包 | 尚无物品／库存系统 | 物品定义、库存规则、操作、界面、保存与联机结果 |
| 个人空间 | 尚无玩家房间系统 | 进入／退出、归属、访问方式、家具摆放、保存 |
| 持久化 | 当前NPC历史和任务进度只在游戏会话 | 角色档案、背包、房间等跨会话保存 |

外部地理覆盖率不等于游戏完成度，也不等于楼内完成度。当前联机是共同场景中的移动与交流原型，还没有完整网游服务端。

## 2. 可以认领的工作包

### A. 集成与开发入口

主要位置：Git仓库、`project.godot`、启动脚本、`campus_game.gd`、团队文档。

负责最新版源码进入共同主线、成员首次运行、PR集成和可试玩版本。维护共享入口，不承包所有模块代码。

当前主线已整合知识 NPC、RAG、Agent、最小联机与动物试验场，并保留公开版的截图与导出调整。后续集成任务是维护成员首次运行、功能 PR 与新的试玩包；在目标电脑确认校园启动、NPC 交互、RAG 地址配置以及主机和客户端加入。

### B. UI与交互设计

主要接入：`campus_game.gd.setup_hud()`、`hero_interactions.gd`、`scene_locator.gd`和联机聊天界面。建议新界面放 `godot/ui/`，该目录目前不存在；先新增一个具体面板即可。

负责视觉风格、角色信息、菜单、窗口布局和输入体验。设计稿先明确角色面板中每个字段的数据来源；没有生命值、等级或装备玩法时，不先填入虚假的数值系统。

首个任务：角色信息面板，只显示已经取得的数据，例如显示名和当前地点，并能开关。完成标准：开启时可操作界面，关闭后恢复控制；与J人物列表、E交谈和聊天输入不抢按键；在团队选定的窗口尺寸可读。背包设计可使用标明为样例的数据展示，但不算库存功能完成。

### C. 玩家角色与动画

主要位置：`third_person_player.gd`、`player_avatar.gd`、`player.gd`、人物GLB与Blender母版。

负责操控、镜头、外观和动画。给UI提供真实角色信息；给联机模块提供可同步的角色表现。不要把账号、背包逻辑放进avatar动画脚本。

首个任务：从已存在模型中确定一个统一玩家形象，检查本地与远端显示一致，并改进一个明确动作或镜头问题。修改外形高度时同步检查眼高、碰撞和相机。

### D. 联机、身份与保存

主要位置：`net_session.gd`、`remote_player.gd`及`campus_game.gd`的联机接线。账号与保存是待新增能力；`campus/ai/`不承担它们。

负责连接、稳定角色ID、服务端状态、保存和客户端请求结果。先约定下一次试玩的人数与玩法，再选择相应服务实现；不先按大型MMO规模拆成多个服务。

首个任务：两位玩家以不同角色身份进入同一场景，重连后识别为原角色。先确定团队账号／身份方案和最小角色档案，再做持久化。网络peer ID会随连接变化，不能直接作为永久账号ID。

当前客户端自报位置可继续作为移动原型；涉及获得／消耗物品和多人房间编辑时，结果必须由负责共享状态的一端决定。

### E. 物品与背包

当前没有实现。可从一个独立库存逻辑文件、一份物品定义和一个背包界面开始；不需要先设计交易、装备、合成或经济系统。

负责物品ID、数量、容量规则、获得与使用，以及向UI暴露库存变化。与D共同约定角色ID、保存和联机请求。

首个任务：领取一个有明确用途的校园纪念物，背包中出现；使用后发生一个可观察效果或数量变化。容量、堆叠和使用效果在该任务中明确一次。

建议分两步验收：先完成单机逻辑和UI；再完成联机与保存。后一步要验证同一玩家重登保留物品，其他玩家不会获得其库存，客户端重复操作不会导致服务器重复发放。这些直接对应真实多人资产操作，不作为所有模块的通用流程。

### F. 校园外部与建筑室内

主要位置：片区构建脚本、`scene_modules.gd`、`data/`、建筑GLB、Blender母版。建议按具体楼或区域分工。

负责建筑外观、室内、地面与设施、出入口、碰撞和区域性能。先做一栋楼的可进入样板，不要求把全部建筑同时做空心。

首个任务：选择一栋有实际使用场景的建筑，制作一间可进入的公共室内。完成标准：校园入口清晰、能进入、室内可走、能返回校园，角色和相机不会卡在门或墙里。

室内先确定用途：展厅、社团活动室或教学展示。只需公共空间时不要求先实现个人房间归属；独立室内场景还是连续加载，由该建筑的尺寸和体验决定。

### G. 个人空间

当前没有实现。与公共建筑室内分开领任务；可以复用室内资产和交互方式。

负责“谁的空间、如何访问、能放什么、如何保存”。初版建议一个角色对应一个房间，支持进入、退出和摆放一种家具；好友权限、扩建和多人编辑后续再做。

依赖D提供稳定角色ID与保存；依赖F或美术提供房间和家具；与E明确家具是否从库存消耗，避免背包和房间各记一份独立数量。

首个完成标准：A进入A房间并摆放家具，离开再进仍存在；B不会误进入自己的“A房间副本”。若做访客功能，再验收B能看见A保存的布局。联网房间ID不能只用本机文件路径代替。

### H. NPC、AI与校园内容

主要位置：`hero_interactions.gd`、`hero_actor.gd`、人物JSON、`campus/ai/`及资料来源。

负责人物知识、动作、回答来源、导览与具体校园互动。继续共用现有角色／检索实现；通常不需要给每位角色单独训练模型。

首个任务：挑一个角色，围绕一个真实用途打磨，例如图书借阅咨询。交付建议问题、有效原文、回答和交谈体验；再与E接入一项纪念物领取任务。

领取物品是游戏状态变化，应通过库存／服务端完成；模型生成“已经送给你”不等于实际发放。多人时明确每人独立对话，是否共享NPC位置与动作再单独确定。

## 3. 先约定这些模块连接点

下表是待共同确认的边界，不是已经实现的接口，也不要求预先建立通用事件总线或接口框架。

| 连接双方 | 最小约定 |
|---|---|
| 身份 → 玩家、背包、房间 | 一个稳定角色ID；网络连接ID另记 |
| 背包 → UI | 提供物品列表、数量及变化通知；UI发送操作意图，不自行修改权威数量 |
| 客户端 → 共享状态服务 | 携带角色与操作所需参数，服务端返回结果；身份以后按实际登录连接确定 |
| 建筑 → 玩家 | 明确入口、出生点与出口位置；切场景后恢复控制和相机 |
| UI → 玩家控制 | 谁打开谁关闭、鼠标状态、移动暂停；两个窗口同时存在时不能提前恢复移动 |
| 房间 → 背包／保存 | 家具从何而来、摆放归属哪个房间、提交后保存哪些变换 |
| NPC → 背包 | 游戏逻辑确认条件并请求发物品；LLM文本只负责解释 |
| 资产 → 场景 | 稳定资源路径、米制比例、朝向、原点和必要动作／节点命名 |

## 4. 用一个完整体验安排先后

第一批：共同源码与新人运行打通。各成员基于同一提交，认领职责与具体文件，先修复启动路径和源码版本脱节。

第二批：角色信息UI、玩家形象、一个建筑室内、一个NPC内容改进可以并行；身份与保存方案同期确定。UI先只展示真实已有数据。

第三批：做“登录／进入校园 → 找到NPC → 领取纪念物 → 打开背包看到物品 → 进入自己的房间摆放 → 重新进入仍保留”的完整体验。多人加入同一校园并看见彼此，背包和房间归属仍分别正确。

第四批：根据首轮团队试玩结果打磨人物、美术、室内、UI和连接体验，再扩展社交、活动与校园服务。不在首批任务中同时铺开全部网游系统。

## 5. 一条适合领取的任务怎么写

示例：为角色信息面板增加开关。

- 玩家结果：按约定入口显示显示名和所在区域，关闭回到游戏。
- 修改范围：新增独立UI场景／脚本，游戏入口只增加挂接；若需要区域名称，由定位模块提供。
- 依赖：设计提供布局，玩家模块提供可用数据和控制开关。
- 验证：打开／关闭、对话中打开、关闭后继续移动、目标窗口尺寸。
- 不包含：等级、装备、生命值、背包和账号后端。

每条任务写到可以独立演示即可。负责人名单、排期和第一栋室内建筑由团队实际人员与用途决定，本指南不虚构这些决定。
